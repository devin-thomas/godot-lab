# LAB-006: Memory archive

Scenario: `persistence`. State: automated-verified on the recorded Windows build, including fresh-process restart; human/device gates deferred. See BUILD_STATUS for evidence.

Save earned lab seals and comfort settings, then reload them from disk through a fresh store reader. Durable local state becomes an inspectable game mechanism rather than an invisible implementation detail. This foundation does not save arbitrary positions or offer general save slots.

## Play and reset

The lab's SAVE & RELOAD operation writes schema 1 and displays a fresh-reader receipt. Ordinary play uses `user://godot-lab/progress.json`; automation uses separate demo-owned storage. R rebuilds the room and preserves earned seals. Malformed progress is rejected and preserved until the user explicitly saves a checkpoint. The baseline requires no account or cloud.

## Acceptance

Verify round-trip values, a second-process reload, missing-file first run, malformed/truncated input, version validation, and unknown lab rejection. Surface failed reads/writes using the project's visible error convention. Preserve invalid input until the explicit repair action. Confirm that an operation and its scenario use the same store implementation.

Capture can demonstrate the visible state change; restart/file assertions establish persistence. A memory-only restore does not satisfy the durable-state claim.
