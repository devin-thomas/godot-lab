### Player payoff

Invoke one typed operation from UI and automation and compare receipts and undo.

### Mechanisms and operations

Mechanism leads (verify installed APIs; lab-owned types/contracts are proposals):

- Callable
- Signal
- proposed OperationEnvelope contract

Proposed typed operations, shared by player UI and supported scenario/CLI/live/MCP adapters:

- `operations.invoke(request:OperationEnvelope)->OperationReceipt`
- `operations.undo(receipt_id:String)->OperationReceipt`

Before A closes, specify each operation's bounded argument/result schema, readiness, revision/idempotency, event effects and cancellation behavior in source. Names alone are not an implementation.

### Interaction

1. Inspect an operation schema
2. Perform it through a control
3. Repeat via scenario with same request ID
4. Undo one committed change

### Fixture, reset and unavailable path

Scenario: `operation-desk`. Fixture: Original object-color/position domain with stable IDs and request ledger.

Reset ownership: Restore fixture ledger and only its receipts.

Limits and unavailable route: Proposed lab-owned contract, not arbitrary remote code execution.

Use original bounded fixtures with hash/license/seed manifests. Readiness must name the actual missing adapter and a useful labeled fallback if possible. Fixture replay does not establish device/provider support.

### Positive acceptance

- UI/scenario yield equivalent state
- Duplicate request mutates once
- Undo restores exact prior state
- Failed validation emits error receipt

### Failure and negative controls

- Ambiguous target refuses mutation
- Stale revision rejects with current revision

Additionally exercise reset/exit during the longest operation, repeated entry and fixture isolation. Observe real mechanisms; never assign the expected final result to make the assertion pass.
