# Why Godot Lab exists

An engine exposes more useful mechanisms than a typical game ever needs. Knowing those mechanisms expands the kinds of games and tools a developer can imagine. Documentation explains the API; a small playable experiment reveals the consequences of using it.

Godot Lab takes the living-documentation pattern of [Apple Native Capability Lab](https://github.com/devin-thomas/apple-native-lab) into a different domain. It combines written intent, a bounded implementation, and evidence that a user can inspect. The examples form a coherent playable place rather than a disconnected directory of code fragments.

The key systems idea is reusable scenes with repeatable actions. A player's movement, a resettable physics arrangement, and a deterministic camera route can serve both ordinary play and automated inspection. Cappy can record those scenarios through its official package. FFmpeg can inspect frames, timing, and audio. Assertions can explain what changed. All three forms are useful; none replaces the others.

The art is an original interpretation of texture-first early 3D: angular forms, painted surfaces, deliberate shade shapes, strong silhouettes, and restrained atmosphere. Contemporary rendering is welcome when it teaches a specific capability. A nostalgic filter cannot compensate for weak composition or inaccessible instructions.

This repository is the complete public core: playable source, original fixtures, documentation, tests, and public-safe evidence summaries. Its build and learning path must remain independent. Optional capture adapters are not runtime dependencies. Raw takes, credentials, machine paths, and unpublished reference material do not belong in its history.
